## Scaling Limits and Recommendations

- **Connection pools**: The indexer runs a read pool (default 10) + write pool (default 3). Increase `DB_CONNECTION_LIMIT` to 20 before scaling API replicas past 2 pods.
- **Redis**: With 30 s TTLs and a standard dataset, Redis stays well under 100 MB. Increase `maxmemory` only if large JSON payloads (e.g., bulk IPFS metadata) are cached.
- **SSE connections**: The server caps connections at `MAX_SSE_CONNECTIONS` (default 500). Beyond that, clients receive HTTP 503. Use a WebSocket fan-out proxy (Ably, Pusher) for >500 concurrent listeners.
- **Ingestion throughput**: The write pool of 3 connections handles ~150–300 events/s comfortably. Add a second poller instance (partitioned `TRACKED_CONTRACTS`) to exceed 500 events/s without pool exhaustion.
- **Full-text search**: `GET /listings?search=` uses a GIN-indexed tsvector; ≥3-char term queries stay under 50 ms at 2 000 listings. Short-term ILIKE fallback is O(n); avoid it in production by ensuring all listings have their `searchVector` populated via the IPFS queue worker.
